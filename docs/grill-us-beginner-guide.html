03

로그인은 어떻게 동작하나요?

비밀번호를 우리 앱이 받지 않고 Microsoft 로그인 페이지에 맡깁니다.

사용자가 보호된 Games 메뉴를 엽니다.

ProtectedRoute가 로그인 여부를 확인하고, 돌아올 주소를 안전하게 저장합니다.

Microsoft 로그인 페이지로 이동합니다.

아이디와 비밀번호는 Grill Us가 아니라 Microsoft가 처리합니다.

로그인이 끝나면 원래 페이지로 돌아옵니다.

MSAL이 redirect 응답을 읽고 브라우저의 sessionStorage에 로그인 캐시를 둡니다.

필요한 서비스마다 별도 토큰을 받습니다.

Graph 사진용 토큰과 Grill Us 리더보드 API용 토큰은 서로 바꾸어 쓸 수 없습니다.

서버가 API 토큰을 다시 검증합니다.

화면에서 로그인했다고 서버가 무조건 믿지 않습니다. 서명·발급자·대상·tenant·scope를 모두 확인합니다.

토큰 3가지를 구분하기

로그인 정보 openid profile email 화면에 이름과 이메일을 표시하기 위한 기본 신원
Graph 토큰 User.Read.All 구성원 목록과 48x48 사진을 읽기 위한 열쇠
API 토큰 Leaderboard.Access 우리 Express 리더보드 API에 기록을 보낼 때 쓰는 열쇠

왜 토큰을 나눌까요?

회사 출입증이 있다고 모든 서버실 문이 열리면 위험합니다. Graph용 열쇠는 Graph에서만, 리더보드용 열쇠는 리더보드에서만 작동하게 범위를 좁혔습니다.

서버는 무엇을 검사할까요?

RS256 서명, 정확한 issuer와 audience, tenant ID, UUID 사용자 ID, 이름, Leaderboard.Access scope를 jose와 Zod로 검사합니다. 

// 쉬운 말: “Microsoft가 서명했고, 우리 API에 보낸 토큰인가?”
await jwtVerify(token, jwks, {
  algorithms: ["RS256"],
  audience: ENTRA_API_AUDIENCE,
  issuer: `https://login.microsoftonline.com/${tenantId}/v2.0`,
});

04

DB는 무엇을 저장하나요?

SQLite 파일에는 리더보드 결과와 제출 횟수만 저장합니다.

SQLite란?

별도 DB 서버를 설치하지 않아도 파일 하나로 동작하는 관계형 데이터베이스입니다. 이 프로젝트에서는 개발용 리더보드 장부로 사용합니다. 게임 진행 중 저장은 SQLite가 아니라 브라우저의 localStorage를 사용합니다.

테이블중요 필드역할
leaderboard_results result_id, user_oid, display_name, score, boss*_ms 완료된 게임 결과와 결정론적 정렬 값을 보관
submission_attempts user_oid, attempted_at_ms 사용자별 10분 제출 횟수를 계산해 과도한 요청을 제한

DB를 열 때 적용하는 안전장치

  • WAL: 읽기와 쓰기가 서로 덜 방해하도록 기록 방식을 설정합니다.
  • foreign_keys=ON: 관계 규칙을 SQLite가 확인하게 합니다.
  • busy_timeout=5000: DB가 잠겼을 때 바로 실패하지 않고 최대 5초 기다립니다.
  • user_version=1: DB 구조 버전을 기록해 migration을 한 번만 실행합니다.
  • prepared statement: 사용자 값을 SQL 문자열에 직접 붙이지 않아 SQL injection 위험을 낮춥니다.
-- 점수가 높을수록 먼저, 보스 시간은 짧을수록 먼저
ORDER BY
  score DESC,
  boss_time_sort_ms ASC,
  submitted_at_ms ASC,
  result_id ASC

같은 결과를 두 번 보내면?

네트워크가 끊기면 브라우저가 같은 결과를 다시 보낼 수 있습니다. 서버는 resultId를 영수증 번호처럼 사용합니다. 번호와 내용이 모두 같으면 새 행을 만들지 않고 기존 결과를 돌려줍니다. 번호는 같은데 내용이 다르면 409 RESULT_ID_CONFLICT로 거절합니다. 이것을 멱등성이라고 합니다.

게임은 어떤 방식으로 구현했나요?

React와 Phaser가 서로의 일을 침범하지 않도록 다리 하나로 연결했습니다.

React 게임 준비
HUD·일시정지
결과 화면
↔
GameBridge 상태는 React로
명령은 Phaser로
↔
Phaser 60Hz 계산
충돌·적·보스
Canvas 렌더
자동차 비유

Phaser는 엔진과 바퀴처럼 매 순간 이동·충돌·공격을 계산합니다. React는 속도계와 버튼처럼 정보를 보여주고 명령을 받습니다. GameBridge는 두 장치를 연결하는 배선입니다.

고정 60Hz simulation

화면이 빠른 컴퓨터와 느린 컴퓨터에서 다르게 움직이지 않도록 게임 규칙은 1초에 60번 고정 간격으로 계산합니다. 렌더는 최대 120FPS가 가능하지만 규칙 계산 속도와 분리됩니다.

저장 가능한 난수

XorShift32는 seed와 현재 상태를 저장할 수 있습니다. 같은 저장 상태를 불러오면 난수 순서도 이어져 복원이 예측 가능해집니다. 보안용 암호 난수는 아닙니다.

System 분리

플레이어, 적, 아이템, 각 보스를 별도 System으로 나눴습니다. 한 거대한 파일에 모든 규칙을 넣지 않아 테스트와 수정 범위를 줄입니다.

1280x720 논리 화면

게임 세계의 기준 크기는 1280x720으로 고정하고 Phaser FIT scale이 실제 브라우저 크기에 맞춥니다. 모바일과 데스크톱이 같은 좌표 규칙을 공유합니다.

07

저장과 리더보드는 어떻게 이어지나요?

“게임 진행 저장”과 “완료 결과 제출”은 서로 다른 상자에 둡니다.

Active Save

아직 진행 중인 게임 전체 상태입니다. 계정별 localStorage key에 GameSaveV1 형태로 저장합니다.

  • 플레이어 위치·HP·업그레이드
  • 적·투사체·아이템·보스 상태
  • 게임 시간·난수 상태
  • 구출한 시민 ID

Pending Results

게임은 끝났지만 서버 영수증을 아직 받지 못한 결과의 FIFO 발신함입니다.

  • 현재 로그인 계정 결과만 읽기
  • 맨 앞 결과부터 한 번에 하나 제출
  • 성공한 결과만 제거
  • 검증 실패와 충돌은 사용자 삭제 전까지 유지
게임 중 dirty 표시

상태가 바뀌면 저장할 내용이 생겼다고 표시합니다.

500ms 단위 autosave

매 프레임 저장하지 않고 변경을 모아 브라우저 부담을 줄입니다.

종료 결과를 pending queue에 먼저 추가

네트워크 실패로 결과를 잃지 않게 로컬 발신함에 보관합니다.

서버 제출

로그인·online·feature enabled일 때 현재 계정 결과만 순서대로 전송합니다.

서버 성공 후 제거

201 신규 저장 또는 200 동일 결과 확인을 받은 뒤에만 로컬 queue에서 지웁니다.

실패하면 어떻게 되나요?

401 / 403인증 문제queue 유지, 인증 복구 후 재시도
422 / 409결과 검증·충돌조치 필요 표시, 자동 삭제하지 않음
429너무 많은 요청Retry-After 전 자동 재시도 금지
Network / 5xx연결·서버 문제queue 유지, online 이벤트나 수동 재시도

어디까지 믿고, 어디부터 검사하나요?

브라우저가 보낸 값은 사용자가 바꿀 수 있다고 가정합니다.

  • 클라이언트가 보낸 사용자 ID와 이름은 받지 않고 JWT principal을 사용합니다.
  • 클라이언트 점수는 받지 않고 서버가 같은 점수 공식으로 다시 계산합니다.
  • 보스 순서·최소 시간·전체 시간·처치 수·피격 수의 명백한 조작을 검사합니다.
  • Graph audience 토큰을 leaderboard API 토큰으로 사용할 수 없습니다.
  • JSON body는 16KB로 제한하고 Zod strict schema로 여분 필드를 거부합니다.
  • production에서는 leaderboard dev bypass와 E2E 인증 flag를 활성화할 수 없습니다.
  • 사진 Blob URL은 메모리에만 두고 save, API DTO, SQLite에 넣지 않습니다.
중요한 한계

서버 검증은 “말이 안 되는 기록”을 거르는 장치이지, 게임 전체를 서버가 직접 계산하는 완전한 치트 방지는 아닙니다. 현재 게임 simulation은 브라우저에서 실행됩니다. 높은 보안 수준이 필요하면 장기적으로 서버 권위 게임 구조를 별도로 설계해야 합니다.

문서와 코드에서 자주 만나는 단어를 쉬운 말로 정리했습니다.

SPA
페이지 전체를 매번 새로 받지 않고 React가 화면 일부를 바꾸는 웹 앱입니다.
Redirect Login
우리 페이지에서 Microsoft 로그인 페이지로 갔다가 다시 돌아오는 방식입니다.
JWT
누가 발급했고 누구에게 어떤 권한을 줬는지 서명해 담은 디지털 출입증입니다.
Scope
토큰이 할 수 있는 일을 좁게 적은 권한 이름입니다.
Audience
그 토큰을 받아도 되는 목적지 API입니다.
JWKS
Microsoft가 JWT 서명을 확인하라고 공개한 공개키 묶음입니다.
Migration
DB 구조를 버전별로 안전하게 바꾸는 절차입니다.
Prepared Statement
SQL 뼈대와 사용자 값을 분리해 실행하는 안전한 DB 명령입니다.
Idempotency
같은 요청을 다시 보내도 결과가 중복으로 늘어나지 않는 성질입니다.
Deterministic
같은 시작 상태와 입력이면 같은 결과가 나오는 성질입니다.
Fixed Step
컴퓨터 속도와 무관하게 게임 규칙을 일정한 시간 간격으로 계산하는 방식입니다.
Blob URL
브라우저 메모리 속 파일을 잠깐 화면에 보여주기 위한 임시 주소입니다.
localStorage
현재 브라우저에 데이터를 오래 보관하는 작은 로컬 저장소입니다.
sessionStorage
브라우저 탭 세션 동안 로그인 관련 값을 보관하는 임시 저장소입니다.
Feature Flag
코드를 지우지 않고 기능을 켜거나 끄는 환경 설정 스위치입니다.
E2E Test
사용자가 브라우저에서 누르는 전체 흐름을 처음부터 끝까지 자동 재현하는 테스트입니다.
