# Decisions: Grill Us Entra 로그인과 DEX Survivor

- Date: 2026-09-17
- Status: Confirmed

## D01. 프로젝트 구성
- **Chosen**: 저장소 루트에 Vite + React + TypeScript 애플리케이션을 구성하고 npm을 사용함.
- **Rationale**: 인증 UI와 Phaser 게임을 하나의 SPA에서 제공하면서 빠른 개발 서버와 타입 검사를 활용하기 위함.

## D02. 인증 라이브러리와 테넌트
- **Chosen**: `@azure/msal-browser`와 `@azure/msal-react`를 사용한 Microsoft Entra ID 단일 테넌트 인증.
- **Rationale**: 브라우저 SPA에 적합한 공식 라이브러리로 조직 구성원만 접근하도록 제한하기 위함.

## D03. 로그인 흐름과 캐시
- **Chosen**: 로그인과 로그아웃 모두 redirect 방식으로 처리하고 MSAL 캐시는 `sessionStorage`에 저장함. 캐시된 계정이 있으면 첫 계정을 자동 선택하며 redirect 처리 중에는 전체 화면 로딩을 표시함.
- **Rationale**: 팝업 차단 문제를 피하고 브라우저 세션이 끝난 뒤 인증 상태가 불필요하게 남지 않도록 하기 위함.

## D04. 인증 환경 변수
- **Chosen**: `VITE_ENTRA_CLIENT_ID`, `VITE_ENTRA_TENANT_ID`, `VITE_ENTRA_REDIRECT_URI`를 필수로 사용하며 하나라도 없으면 앱 시작을 중단함.
- **Rationale**: 잘못된 테넌트나 redirect URI로 조용히 동작하는 구성 오류를 초기에 드러내기 위함.

## D05. 라우팅과 접근 제어
- **Chosen**: `/`는 공개 Home, `/games`와 `/games/:gameId`는 인증 필요, `/games/leaderboard`는 리더보드 화면으로 구성함. 로그인 전에도 Games 메뉴는 잠금 상태로 표시하며 보호 경로 직접 접근 시 자동 로그인 후 원래 경로로 복귀함.
- **Rationale**: 공개 진입점은 유지하되 게임과 사용자 데이터 접근은 인증된 구성원에게만 허용하기 위함.

## D06. 셸 UI와 오류 처리
- **Chosen**: 데스크톱 고정 및 모바일 슬라이드 방식의 사이드바에 홈, 게임, 로그인 또는 로그아웃을 제공함. 로그인 사용자 이름과 이메일을 표시하고 인증 오류는 Home에서 재시도할 수 있게 함. 전체 UI 언어는 한국어로 함.
- **Rationale**: 화면 크기에 맞는 일관된 탐색과 복구 가능한 인증 경험을 제공하기 위함.

## D07. 스타일과 아이콘
- **Chosen**: Tailwind CSS와 `lucide-react`를 사용하고 레트로 픽셀 아케이드 시각 언어를 적용함.
- **Rationale**: 게임 테마를 유지하면서 반응형 레이아웃과 접근 가능한 아이콘 컨트롤을 효율적으로 구현하기 위함.

## D08. 게임 등록과 로딩
- **Chosen**: 게임 카드와 메타데이터를 게임 레지스트리에서 관리하고 실제 게임은 `React.lazy`로 지연 로딩함. 등록되지 않은 게임 ID에는 찾을 수 없음 화면을 표시함.
- **Rationale**: 이후 게임 추가 시 라우팅과 카드 UI의 중복을 줄이고 초기 번들에서 Phaser를 분리하기 위함.

## D09. 게임 시작 시점
- **Chosen**: Games 카드의 `게임 시작` 버튼을 눌렀을 때 프로필 준비를 시작하고 `플레이어 준비 중...` 진행 화면 이후 게임을 시작함.
- **Rationale**: 사용자의 명시적인 동작이 있을 때만 Graph 사진 조회와 무거운 게임 로딩을 수행하기 위함.

## D10. Microsoft Graph 권한과 사용자 필터
- **Chosen**: 관리자 사전 동의를 받은 delegated `User.Read.All` 권한을 사용함. `accountEnabled === true`이고 `userType === "Member"`인 활성 내부 구성원만 시민 후보로 선정함.
- **Rationale**: `User.ReadBasic.All`만으로는 활성 여부와 내부 구성원 여부를 정확하게 판별하기 어려우므로 필요한 속성을 조회하기 위함.

## D11. Graph 호출 위치와 사진 수명
- **Chosen**: 브라우저에서 MSAL 액세스 토큰으로 Microsoft Graph를 직접 호출함. 플레이어 본인 사진과 최대 9명의 시민 사진은 48x48 크기만 조회하고 현재 게임 세션 메모리에서만 유지함.
- **Rationale**: 사진이 Express 서버, 로컬 저장소, 로그 또는 리더보드에 전달되거나 장기 보관되지 않게 하기 위함.

## D12. 사진 조회 실패 처리
- **Chosen**: 사진 조회의 `403`과 `404`는 즉시 제외하고, `429`와 `5xx`는 `Retry-After`를 존중하여 최대 2회 재시도함. 본인 사진 실패 시 얼굴 없는 헬멧을 사용하고 시민 사진이 0장이면 시민 없이 1번 보스를 진행함.
- **Rationale**: 권한 또는 사진 부재를 정상적인 폴백으로 처리하고 일시적인 Graph 장애만 제한적으로 복구하기 위함.

## D13. 프로필 사진 사용 동의
- **Chosen**: 전 구성원의 사전 승인이 실제 오프라인 미팅에서 완료된 것으로 전제하고 게임 시작 전 별도 고지는 표시하지 않음.
- **Rationale**: 별도 런타임 동의 절차 없이 이미 확정된 조직 내 승인 범위에서만 사진을 사용하기 위함.

## D14. 게임 엔진과 렌더링 경계
- **Chosen**: Phaser 3가 60Hz 고정 시뮬레이션으로 전투 월드, 충돌, 이펙트를 담당하고 렌더링은 최대 120FPS를 허용함. React는 HUD, 일시정지, 확인 모달과 결과 화면을 담당함.
- **Rationale**: 게임 루프와 애플리케이션 UI의 책임을 분리하면서 고주사율 화면을 지원하기 위함.

## D15. 게임 공간과 일반 적
- **Chosen**: 한 화면 고정형 아레나에서 추적형, 원거리형, 분열형, 중장형의 가상 적 4종을 사용함. 30초마다 밀도가 증가하고 일반 타이머 10분 이후에는 대량 출현함.
- **Rationale**: 모바일에서도 전장을 한눈에 파악하게 하고 역할별 적 조합으로 난도를 높이기 위함.

## D16. 기본 난이도와 플레이어 외형
- **Chosen**: 보통 난이도로 체력 100, 적 접촉 피해 10, 총 피해 20, 검 피해 35를 기본값으로 함. 플레이어는 본인 얼굴이 헬멧 안쪽에 표시되는 픽셀 아케이드 기사임.
- **Rationale**: 약 10회의 기본 접촉 피해를 허용하는 이해하기 쉬운 초기 밸런스와 개인화된 주인공을 제공하기 위함.

## D17. 조작과 능력
- **Chosen**: 데스크톱은 WASD 또는 방향키 이동, 좌클릭 총, 우클릭 검, Space 대시, E 검 폭풍, Q 화면 전체 에너지 폭발을 사용함. 대시는 기본 1회 충전, 3초 회복, 이동 중 무적이며 검 폭풍 쿨타임은 8초임. 모바일은 가상 조이스틱, 터치 버튼과 총 자동 조준을 사용함.
- **Rationale**: 키보드와 포인터 조합의 즉각적인 액션을 제공하고 모바일에서도 같은 전투 기능을 사용할 수 있게 하기 위함.

## D18. 아이템과 성장
- **Chosen**: 적 처치 시 15% 확률로 아이템을 드롭하고 근접 시 자동 획득함. 총 공격력, 총 사거리, 검 공격력·범위, 대시 최대 횟수, 대시 쿨다운 감소, 필살기 즉시 충전의 누적형 6종을 각 상한과 함께 제공함. 필살기 게이지는 시간으로도 충전됨.
- **Rationale**: 플레이 도중 체감 가능한 성장 선택지를 제공하면서 상한으로 무한 강화를 방지하기 위함.

## D19. 성장 시각화
- **Chosen**: 업그레이드 단계에 따라 갑옷, 총기와 탄환, 검과 궤적, 대시 잔상, 필살기 코어 외형을 강화함.
- **Rationale**: 수치 변화가 플레이어 외형과 효과에도 즉시 드러나도록 하기 위함.

## D20. 일반 타이머와 보스 진행
- **Chosen**: 일반 게임 타이머 5분, 10분, 15분에 보스가 등장하며 보스전 동안 일반 타이머를 정지함. 사망하면 즉시 종료되고 세 보스를 모두 처치하면 클리어함.
- **Rationale**: 각 보스전의 소요 시간이 다음 보스 등장 시점을 밀지 않게 하고 명확한 3단계 목표를 제공하기 위함.

## D21. 1번 보스와 시민 구출
- **Chosen**: 가상 얼굴 9개가 뒤섞인 보스가 최대 9명의 내부 구성원 얼굴 시민을 촉수로 구속함. 촉수는 각각 독립 체력과 플레이어 대상 근접 휘두르기를 가지며 파괴 시 시민을 즉시 구출함. 보스 처치 시 남은 시민은 자동 구출됨.
- **Rationale**: 실제 구성원을 공격 대상으로 만들지 않으면서 사진을 구조 대상의 긍정적인 역할로만 사용하기 위함.

## D22. 시민 구출 결과
- **Chosen**: 구출 시민은 연출 후 안전하게 사라지며 구출 수와 시각적 보상만 남김. 점수와 필살기 게이지에는 영향을 주지 않음.
- **Rationale**: 사진이 포함된 시민을 점수 자원으로 취급하지 않고 기존 점수 공식을 단순하게 유지하기 위함.

## D23. 2번 보스
- **Chosen**: 가슴에 `동그라미 재단` 문구가 잘 보이는 네모난 건물형 가상 로봇으로 구성함. 한 손에는 철퇴, 다른 손에는 방패를 들고 철퇴 공격, 가상 적 소환과 충격파를 사용함. 방패, 철퇴 팔, 양쪽 다리, 가슴 코어 순서로 파괴해야 처치할 수 있음.
- **Rationale**: 부위 파괴 순서에 따라 방어, 공격, 이동 능력이 단계적으로 약화되는 명확한 공략 구조를 제공하기 위함.

## D24. 3번 보스
- **Chosen**: 외형 중앙에 `DEX`가 크게 표시된 가상 우주선과 중앙 다면체 에너지 코어로 구성함. 체력 50%에서 2페이즈로 전환하며 회전 탄막 링, 조준 연사, 가장자리 압축 탄막과 이동 안전지대를 혼합함.
- **Rationale**: 최종 보스임을 즉시 식별할 수 있는 외형과 단계적으로 강화되는 탄막 전투를 제공하기 위함.

## D25. 최종 보스 재등장 기믹
- **Chosen**: 3번 보스 체력이 10% 미만이면 잠시 사라지고 체력 60%, 공격력 70%의 약화된 1·2번 보스가 핵심 기믹을 유지한 채 동시에 등장함. 둘을 처치하면 3번 보스가 사라질 당시 체력과 2페이즈 상태로 복귀하고 3초 카운트다운 후 재개함.
- **Rationale**: 앞선 공략을 종합하는 마지막 관문을 만들되 최종 보스 진행도를 초기화하지 않기 위함.

## D26. 저장과 계정 귀속
- **Chosen**: 게임 상태를 `localStorage`에 500ms마다 저장하고 화면 이탈 시 즉시 저장함. 저장 데이터에는 스키마 버전과 Entra object ID를 포함하며 같은 계정만 이어서 할 수 있음. 다른 계정의 저장은 삭제하지 않고 무시하며 버전이 맞지 않으면 폐기함.
- **Rationale**: 갑작스러운 이탈에도 진행을 보존하면서 계정 간 게임 상태와 시민 사용자 ID가 섞이지 않게 하기 위함.

## D27. 일시정지와 재개
- **Chosen**: 화면 이탈 시 Phaser를 일시정지하고 `계속하기` 클릭 후 3초 카운트다운으로 재개함. 재시작 시 `현재 진행 상황이 모두 초기화됩니다. 재시작하시겠습니까?` 확인 모달을 표시하고 재시작 또는 게임 종료까지 저장을 유지함.
- **Rationale**: 복귀 즉시 피격되는 문제와 실수로 진행을 초기화하는 문제를 방지하기 위함.

## D28. 점수 공식
- **Chosen**: 일반 적 처치 `+100`, 피격 `-50`, 클리어 `+10,000`을 적용함. 보스 시간 점수는 각각 `max(0, 120 - seconds) x 20`, `max(0, 180 - seconds) x 20`, `max(0, 300 - seconds) x 20`이며 등장부터 처치까지의 일시정지 제외 시간을 사용함. 사망해도 이미 처치한 보스 기록은 반영함.
- **Rationale**: 공격적 플레이, 회피와 빠른 보스 공략을 모두 보상하면서 음수 시간 보너스를 방지하기 위함.

## D29. 결과 제출 시점과 재시도
- **Chosen**: 사망 또는 3번 보스 처치로 정상 종료된 결과만 제출하고 재시작과 중도 이탈은 제출하지 않음. 실패한 제출은 `resultId`와 Entra object ID를 묶어 로컬에 보류하고 같은 계정만 재시도할 수 있으며 성공 또는 직접 삭제까지 유지함.
- **Rationale**: 완결된 플레이만 순위에 포함하고 네트워크 오류로 결과가 유실되거나 다른 계정으로 제출되는 일을 막기 위함.

## D30. 개발용 공용 리더보드
- **Chosen**: Express, Zod와 `better-sqlite3`로 개발 전용 공용 Top 10 API를 `server/`에 구성함. 모든 결과는 별도 행으로 저장하여 한 사용자가 여러 순위를 차지할 수 있음.
- **Rationale**: 별도 클라우드 인프라 없이 여러 브라우저가 공유하는 개발 리더보드를 빠르게 검증하기 위함.

## D31. 리더보드 표시와 정렬
- **Chosen**: Entra `displayName`, 점수, 결과, 처치 수, 피격 수와 보스별 시간을 표시하고 이메일은 제외함. 점수 내림차순, 보스 시간 합 오름차순, 먼저 제출한 순서로 정렬함.
- **Rationale**: 최소한의 식별 정보만 노출하면서 동점 순서를 결정론적으로 정하기 위함.

## D32. 리더보드 인증 우회
- **Chosen**: Entra 앱에 `Leaderboard.Access` 커스텀 API scope를 노출하고 SPA가 Express용 액세스 토큰을 별도로 획득함. Express는 issuer, audience, 만료, scope를 검증하여 `oid`와 `name`을 신뢰함. 개발 우회는 기본 `false`이며 비운영 환경에서 명시적으로 활성화한 경우에만 `LEADERBOARD_DEV_USER_ID`, `LEADERBOARD_DEV_DISPLAY_NAME`을 사용함.
- **Rationale**: Microsoft Graph 대상 토큰을 자체 API 인증에 오용하지 않고 공용 개발 리더보드에서도 실제 사용자를 안전하게 구분하기 위함.

## D33. 제출 검증과 보안 수준
- **Chosen**: 서버는 Zod로 타입과 범위를 검증하고 최소 플레이 시간, 보스 시간, 점수 공식, 제출 빈도를 재검증함. 전체 이벤트 재생이나 서버 권위 전투는 구현하지 않으므로 완전한 클라이언트 조작 방지는 보장하지 않음.
- **Rationale**: 개발 프로토타입에 적합한 비용으로 명백히 잘못된 결과를 차단하고 보안 한계를 명시하기 위함.

## D34. 운영 범위
- **Chosen**: 커스텀 API scope와 Bearer JWT 검증은 이번 범위에 포함하되 리더보드 기능 자체는 개발 전용으로 유지하고 운영 배포 대상에서는 메뉴, 경로, 조회와 제출을 모두 비활성화함.
- **Rationale**: 개발 환경에서도 사용자별 기록의 신원을 검증하면서 리더보드 저장소와 API가 운영 기능으로 노출되는 위험을 피하기 위함.

## D35. 로컬 실행과 API 연결
- **Chosen**: `npm run dev` 한 번으로 `concurrently`를 통해 Vite와 Express를 실행하고 Vite가 `/api` 요청을 Express로 프록시함. SQLite 데이터는 `server/data/`에 저장함.
- **Rationale**: 프론트엔드와 API의 개발 시작 절차를 단순화하고 브라우저의 API 주소 구성을 일관되게 유지하기 위함.

## D36. 테스트 전략
- **Chosen**: Vitest와 React Testing Library로 UI 및 순수 규칙을 검증하고 Playwright로 Phaser 게임 진입, 일시정지, 복원과 종료의 브라우저 스모크 테스트를 수행함.
- **Rationale**: 랜덤성과 캔버스에 덜 의존하는 규칙은 빠르고 결정론적으로 검사하고 실제 통합 흐름은 브라우저에서 확인하기 위함.

## D37. 자동으로 확정한 구현 세부사항
- **Chosen**: 리더보드 API는 인증된 사용자 식별자를 서버에서 결정하고 클라이언트가 보낸 사용자 ID나 표시 이름을 신뢰하지 않음. 점수는 서버가 제출 통계로 다시 계산하며 `resultId`에 고유 제약을 두어 중복 재시도를 멱등 처리함.
- **Rationale**: 이미 확정된 서버 검증, 계정 귀속과 재시도 정책을 만족하려면 클라이언트 신원 신뢰와 중복 저장을 차단해야 하기 때문임.
